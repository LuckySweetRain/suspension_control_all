1. Introduction
Mechanical Simulation Corporation produces and distributes software tools for simulating and
analyzing the dynamic behavior of motor vehicles. The simulation software packages are
organized into families of products named CarSim®, TruckSim®, BikeSim®, and
SuspensionSim®. All are based on the simulation architecture named VehicleSim®.
All of these products include VS Visualizer, a program for viewing two-dimensional plots and 3D
animations based on VehicleSim simulation data. When operated as a post-processing tool, VS
Visualizer uses pre-recorded simulation data loaded from VS or ERD files that are generated by
the simulation program. When used for live animation, VS Visualizer receives a live feed of
streaming information from the simulation program.


Who Should Read this Manual
This manual focuses on aspects of VS Visualizer that are independent of its use in a VehicleSim
product such as CarSim. Details of the VehicleSim data screens associated with VS Visualizer are
covered in the documentation for those screens and are not repeated here.
Occasional users of a VehicleSim product who set up all runs and visualization options from the
VehicleSim Browser might not need the information in this manual.
This manual is intended for users who wish to know the details of the full capabilities of VS
Visualizer, and how it obtains necessary information from input files.
This manual assumes some familiarity with a VehicleSim product. If you are new to the software,
you should first complete the Quick Start Guide for your VehicleSim product, which covers the
basic use of VS Visualizer for looking at videos and plots based of simulation results. We also
recommend that you read the beginning of the VS Browser manual to learn how the database is
managed and how the VehicleSim Browser graphical user interface (GUI) works.


Notational Conventions
“VS Browser” is the main program of the product that provides the GUI and accesses the
database (e.g., carsim.exe).
 “VS Solver” is a program within a VehicleSim product such as CarSim that reads input files,
calculates variables from an internal math model, and writes output files.
“VS Math Model” is the set of equations within a specific VS Solver.
When showing the syntax for data, words shown in the Courier font indicate specific literal
keywords or file names; words in italics indicate the name of the item whose value can vary in
different situations, and square brackets [like this] indicate that the content between the brackets
is optional.

2. Window and Panel Organization
VS Visualizer supports multiple windows and panels, shown in multiple modes. Originally
introduced for real-time realistic animation for driving simulators, it has been extended in support
of real-time applications with synchronized full-screen displays on multiple monitors, to
engineering post-processing involving combinations of video camera views and plots.
Regardless of the layout of windows and display areas, all views of data are synchronized with a
single set of time controllers.


Types of Panels
VS Visualizer has a main window with a title and menu bar, along with one fixed panel that
cannot be closed or undocked. It supports five types of panels, shown in Figure 1 and described
below.




                    Figure 1. Example layout showing all five types of panels.
    A video panel shows an animated view from a simulated video camera. VS Visualizer
       supported multiple video panels in both live and post-processing applications.



                                              5 / 107
    A single Simulation Timer panel has controls for displaying and controlling the recorded time
        when VS Visualizer is used for post-processing visualization. This panel is not shown
        when VS Visualizer is used for a live feed of motion information.
    A plot panel shows graphical cross plots of values of variables recorded in a simulation VS or
        ERD file. VS Visualizer supports multiple plot panels for post-processing; this option is
        not supported for live animation.
    A plot grid is a panel of plot panels. VS Visualizer supports multiple grid panels for post-
       processing. Plot grids are not supported for live animation.
    A single Data Manager panel lists all of the variables whose values are recorded in all
       attached VS and ERD files. This panel is not available for live animation.
VS Visualizer can be launched in one of three modes for determining the initial appearance.
These three modes correspond to the three visualization buttons in the upper-right region of the
Run Control screen in a VS Browser:
    1. Video only: this mode is used when you click the Video button. VS Visualizer initially
       shows a fixed video panel that cannot be undocked. Additional panels for video and
       plotting can be added using the menu bar controls.
    Plot grid only: this mode is used when you click the Plot button. VS Visualizer initially
        shows a fixed plot grid panel. Additional panels for video and plotting can be added using
        the menu bar controls.
    Video + Plot: this mode is used when you click the Video + Plot button. VS Visualizer
       initially shows a fixed plot grid panel, plus a docked video panel that can be undocked.
       This mode is the same as would be obtained by starting in the plot grid model and then
       adding a video panel. Additional panels for video and plotting can be added using the
       menu bar controls.
At any time, there can be no more than one visible Simulation Timer control panel or dataset
manager panel. VS Visualizer supports multiple instances of the other three types of panels.
Except for the fixed panel (video or plot grid) shown when VS Visualizer is launched, all of the
panels can be moved, resized, docked, undocked, and closed.
Because all of the panels are synchronizes, the images from video panels always show views for
the single time as controlled by the Simulation Timer. If you wish to see views of the simulation
at different times, then simply launch a separate instance of VS Visualizer. For example, click the
Video button on your Run Control screen again.

3. Viewing Simulated Video
This chapter begins with a general overview of how you view video from a simulated camera
with VS Visualizer, and then proceeds to describe how you can control it interactively.


Overview of Video Simulation
Imagine that you are aiming a video camera at a vehicle as it moves down the road. Thirty times
per second, the camera records an image of the vehicle and ground as seen from your point of
view. By playing back those images at the same rate (thirty times per second), you see the vehicle
move relative to its surroundings.
If the camera has a zoom lens, you can zoom in to fill the screen with the vehicle or you can
zoom out to shrink its apparent size.
What you see depends, in part, on where you are located. You could be standing on the ground
observing the moving vehicle, in which case your position will not change. You could be an
occupant of the vehicle, in which case your viewing position within the 3D world will change as
the vehicle moves.
Your view is also determined by how you aim the camera. You might have the camera aimed at a
fixed point in space. In this case, the vehicle would only be visible while it is in the field of the
camera view. More likely, you would move and aim the camera as needed to keep the vehicle in
view.
The external camera in VS Visualizer is aimed directly at a target called the look point. Figure 4
shows the geometric relationship between the camera point and the look point. You can control
this relationship interactively in VS Visualizer using simple sweeping movements of the mouse.




             Figure 4. Geometry of the camera point, look point, and occupant view.
VS Visualizer also supports describing the camera’s relationship to the target in terms of an
Occupant View. Using this method, the position of the camera is located at the Occupant View
Location that represents the eye point of a virtual occupant of the vehicle. The direction the
camera is pointed can be controlled by changing its Tilt and Swivel angles.
VS Visualizer is normally launched from a VS Browser by clicking a Video or Plot button from
the Run Control screen. When the button has “Video” in the name, a dataset from the VS

Improving Video Performance
The speed at which VS Visualizer can render the 3D scene (the frame rate) depends on the overall
speed of the computer, the size of the animation window, the number of surface polygons being



                                           13 / 107
drawn, and the level of detail in textures associated with the surface shapes, in addition to other
factors. However, just as importantly, the speed depends on the type of video/graphics hardware
in the computer and the operating system settings of the graphics hardware.
VS Visualizer uses the OpenGL library for 3D rendering. Some video cards are able to execute
portions of OpenGL in specialized hardware that can dramatically increases rendering
performance.
VS Visualizer has two modes of operation for rendering visualization data. The Standard Mode of
operation is to use modern rendering techniques involving per-pixel lighting and other advanced
effects. A Compatibility Mode is available for use with less capable computer hardware. In
general, Standard Mode will produce results of higher visual quality at a lower frame rate, while
Compatibility Mode will produce lower visual quality at a higher frame rate.
The VS Visualizer default behavior is to automatically select the render mode, based on the
capabilities of your hardware (reported by the installed video driver). If you believe that VS
Visualizer is making the wrong automatic choice, you may manually set the render mode using
the Preferences dialog (see page 33).
Detailed information on your reported hardware capabilities can be viewed by selecting Show
Log File from the Help menu.
In Standard Rendering Mode, VS Visualizer supports advanced rendering features such as per-
pixel lighting, normal mapped surfaces, and dynamic shadows that require intense computation to
generate images. These place even more requirements on the graphics video cards. Video cards
older than about 2006 do not always provide full support for all of VS Visualizer’s graphical
features. Desktop computers can usually be upgraded inexpensively by replacing the video card
to obtain increased performance with VS Visualizer. Video cards that work well with VS
Visualizer include:
        §   AMD/ATI video cards that use the Radeon chipset, and
        §   Video cards that use the NVIDIA GeForce chipset.
With laptop computers, upgrading is not always an option, so you should consider the graphics
capability of a laptop when deciding which kind of hardware to use with VS Visualizer.
When using the Windows operating system, these settings can affect the performance of VS
Visualizer:
    1. Color Depth (number of colors). OpenGL does not work well with 256 colors or less.
       The valid settings are 16-bit (64 thousand colors), 24-bit (16 million colors), and 32-bit
       (also called true color). Modern video cards work best in 32-bit color mode. Experiment
       to find which works best for your machine.
    2. Screen Size. On some laptops, the native size (e.g., 1600 x 900) updates faster than other
       sizes. As with the colors, experiment on your machine to find out if there are differences
       in VS Visualizer speed with the different settings.
    3. Graphics Acceleration. In some implementations (details depend on your version of
       Windows and on the installed hardware), various levels of graphic acceleration can be



                                             14 / 107
        set. In some cases, the fully accelerated mode will cause display problems and system
        crashes. If this happens, try different acceleration settings.

Aspect Ratio Control
There are a few ways to control the aspect ratio of a selected plot. Users can lock/unlock the
aspect ratio by using the shortcut u, in Figure 13. There is also an option to lock/unlock in the
right-click plot area context menu, in Figure 16 on page 21. In the plot area context menu, the

While the aspect ratio is locked, the plot will maintain its shape even if the plot window is
resized, any method of zooming in/out, or if zoom is used on a specific axis. For example, while
locked aspect ratio is active, when performing a vertical axis zoom the horizontal axis will
automatically adjust to keep the proper aspect ratio. If the aspect ratio is unlocked, the plot will
stretch in only the horizontal or vertical direction.


5. Adding Data to a Plot
When you launch VS Visualizer from a VS Browser using button from the Run Control screen
(Video, Plot, or Video + Plot), a set of predefined plots are available for immediate viewing.
Even if the plot grid is not shown initially, the Plot menu gives access to the plot descriptions that
were linked in some way to the Run Control dataset.
However, if the checkbox Write all outputs on the Run Control screen is checked, there can be
thousands of variables in the VS or ERD output file generated when a simulation is run. There are
several ways that you can create new plots interactively involving other variables whose values
are recorded in the files.


Set Up Additional Plots from the VS Browser
A typical Run Control dataset is set up to show between 5 and 20 plots when you click the Plot
or Video + Plot button. The database typically has at least 200 plot setups that can be added
simply by making links to them, typically from the Run Control screen. This is shown by
example in the Quick Start Guide.
Another option is to create new Plot Setup datasets from the VS Browser. The method is also
shown by example in the Quick Start Guide.
An advantage of the approach of adding datasets to the product database via the VS Browser is
that the plot definitions work with overlays and are available for future simulations.


Add Plot Data from within VS Visualizer
Although it is always possible to add new plot setups to your VS database, there are times that
you might want to quickly view more data immediately from within VS Visualizer. There are two
options for adding data to an existing plot: drag and drop, and typing variable names.

To access this feature, locate the Data Manager window by navigating to View > Data
Manager. It will show the VS and ERD files that are currently available. Expand a file name to

14. Input Files
This chapter provides reference information about the files read by VS Visualizer.
When VS Visualizer is started from a VS Browser screen clicking a button on the Run Control
screen, the files necessary to view the simulation results are automatically opened. Therefore, it is
not necessary to know the names of the input files for ordinary use. However, if you want to use
VS Visualizer in advanced and/or non-standard ways, it is helpful to understand how the VS
Browser, VS Solver, and VS Visualizer interact, and how VS Visualizer reads input data.
When VS Visualizer is used to view a previously executed simulation, all motion information is
obtained from files. This mode of operation is referred to as “post processing.” When VS
Visualizer is used for Live Animation (e.g. for a driving simulator or to monitor real-time
simulation), the motion information is obtained from a network connection to the VS Solver.
This chapter describes the more common post-processing mode of operation. There are only a
few differences between this mode and Live Animation, and those differences are covered in
Chapter 21.


Primary Input Files
VS Visualizer uses three file types as primary input: Parsfiles, VS or ERD text header files, and
BIN or VSB binary files.

Parsfiles
Parsfiles are text files (with the extension PAR) that are typically generated by the VS Browser
based on data entered by the user on the screens linked to a Run Control dataset. Parsfiles may
also be created and edited directly using a text editor.
Parsfiles may contain several types of information. For example, a single Parsfile may contain
simulation parameters read by a VS Solver to configure the simulation (e.g. the mass of a
vehicle), as well as parameters read by VS Visualizer to configure the display of the simulation
results (e.g. the 3D shape file that represents the vehicle visually). In this case, the VS Solver
ignores the parameters intended for VS Visualizer, and VS Visualizer ignores the parameters
intended for the VS Solver.

VS and ERD files
When a simulation is run, outputs are written into a binary file for later use by VS Visualizer or
other post-processing software. In older versions of the software, the ERD/Bin format has been
used. Starting with the introduction of CarSim 9.0 (2014), a newer format called VS is also
available. VS Visualizer supports both types of files.
The VS or ERD files are generated by the VS Solver and contain the results data for a simulation.
The VS or ERD file is a text file that contains a description of the simulation variables (e.g. the
names of the variables, their units, the simulation time-step, etc.), and description of the layout of
a corresponding binary file that contains only numbers that indicate the value of each simulation
variable at each time-step.




                                              40 / 107
Figure 42 illustrates how these files are generated by the VS Browser and VS Solver, and then
used by VS Visualizer to display the simulation Run.




                 Figure 42. Operation of VS Visualizer in a VehicleSim product.
Pressing the Run Math Model button in the VS Browser initiates the process of generating the
input files that VS Visualizer uses. The automated sequence consists of these steps:
    1. The VS Browser generates one or more Parsfiles that contain configuration parameters
       for both the VS Solver and VS Visualizer. Typically, a single Parsfile named
       Run_###_all.par is generated in the Runs folder of the VS Browser database,
       where “###” represents a computer-generated 36-character Universally Unique ID
       (UUID).
    2. The VS Solver is automatically executed and instructed to open the generated Parsfile(s).
    3. The VS Solver reads the simulation parameters specified in the Parsfile(s) and executes
       the simulation.
    4. The VS Solver writes the simulation results (motion variables, etc.) to two files, an ERD
       (or VS) and a BIN (or VSB) file.
To view the results of the simulation, the user presses the Video button in the VS Browser, which
initiates the following sequence of events:
    1. The VS Browser re-generates the Run_###_all.par file (in case the user has
       changed animation or plot setup data since the simulation was run).
    2. The VS Browser generates a Parsfile named Animator.par. This file contains links to
       the Run_###_all.par file and the VS/ERD header file, as well as additional
       configuration information. If multiple runs are overlaid, Animator.par contains links
       to the PAR and VS/ERD file for each run.




                                            41 / 107
    3. VS Visualizer is executed and instructed to load the Animator.par file.
    4. VS Visualizer loads the Animator.par file, which in turn causes it to load the
       Run_###_all.par file and the VS/ERD header file for each Run. VS Visualizer
       automatically loads the VSB/BIN file when it loads a corresponding VS/ERD file.

CSV files
When a simulation is run, outputs can also be written into an Excel CSV file, which is of excel
format, for later use by VS Visualizer or other post-processing software. When the output type
specified is Excel CSV, the VS Solver generates a CSV file and a VS file containing the results
data for a simulation.
The VS Visualizer, given a CSV file, also reads the associated VS file for header information and
simulation time-step, and the CSV file for data. If the VS Visualizer does not find an associated
VS file, or the data in the VS file is different from the CSV file, the VS Visualizer would just
ignore the VS file and get the header information, simulation time-step and data from the CSV
file.


Secondary Input Files
Secondary input files are files used only by VS Visualizer, which are identified with keywords
encountered in Parsfiles.

Shape Files
Shape files define 3D geometric shapes and possibly associated material properties. 3D modeling
programs and CAD programs are used to create these files. VS Visualizer reads several standard
shape file formats, including:
   ·   OpenSceneGraph (OSG) files. This file format enables advanced material properties
       to be utilized. Details about the OSG file format are available from the
       OpenSceneGraph web site (http://www.openscenegraph.org/).
       There are multiple file formats for OSG shape files. VS Visualizer can load and
       display all four standard OSG version 3.4 standard formats which have extensions
       OSG, IVE, OSGT, and OSGB. However, only the text-based formats are supported
       for generating VSRAP files. OSG and OSGT are text-based formats, while IVE and
       OSGB are binary formats.
   ·   Wavefront (OBJ) surface files define 3D shapes, and refer to material properties
       including color, lighting properties, and textures. OBJ files can optionally link to MTL
       material files that in turn define the materials that are named in the OBJ files. The
       MTL file lists lighting properties for each material, and identifies an associated
       graphic file (JPG, BMP, DDS, and other formats) that defines a texture associated
       with the material. Note that OBJ files are not capable of using the advanced material
       properties available with the OSG format.
   ·   Stereolithography (STL) surface files define 3D shapes as a group of triangles. STL
       files are not capable of using texture maps like OBJ files, nor material properties
       available with the OSG format.


                                             42 / 107
Audio Files
Audio files are used by VS Visualizer to generate sounds during the animation.
For detailed information about the audio file types supported by VS Visualizer, see Chapter 20:
Audio (page 77).


15. VehicleSim Results Analysis Packages
A VehicleSim Results Analysis Package (VSRAP) is an input file for VS Visualizer which
contains all of the necessary data to analyze, via animation and/or plotting, the results of one or
more simulation runs. VSRAP files typically have the file extension “vsrap”. A VSRAP file can
be created by VS Visualizer on one computer, and then transferred to another computer where it
can be opened with VS Visualizer. The second computer does not need to have the VehicleSim
product (e.g. CarSim) installed because the VSRAP file is completely self-contained.
VSRAP files can be created manually using the main window drop down menu option, or by
specifying the command line option -vsrap "<filename>". If the command line option is
used, VS Visualizer will load the specified Parsfile, convert it to a VSRAP, and then close
automatically.
By default, VS Visualizer will not overwrite an existing file when creating a VSRAP file using
the command line option. To instruct VS Visualizer to overwrite an existing file, also specify the
command line parameter -vsrapoverwrite. For example:
VsViualizer -vsrap "animation.vsrap" -vsrapoverwrite "animator.par"


16. Entities and Parsing
VS Visualizer’s operation relies on a set of internal components called VS Visualizer Entities, or
simply Entities. Most of VS Visualizer’s Entity types are directly related to objects defined
within Parsfiles. For example, when the keyword ADD_REFERENCE_FRAME is read from a
Parsfile, a new Reference Frame Entity is created within VS Visualizer.
There are many different types of Entities that can be loaded from a Parsfile. Understanding the
properties of these Entities, their relationships to each other, and how their information is loaded
from Parsfiles is crucial to being able to use VS Visualizer in advanced ways.
Details of all Parsfile keywords that may be used for all VS Visualizer Entities can be found
elsewhere in this manual. This section describes the high-level characteristics of Entities, and
how different types of Entities relate to, and interact with, one another.


Entity Relationships
Entities are related with parent-child relationships that form a tree-like structure. For example, a
Simulation Run “contains” child Entities that are Reference Frames. Reference Frames contain
child Entities that are Shapes and Sounds. Figure 43 shows some of the VS Visualizer Entities
and their relationships.




                                             43 / 107
Entity Types
There are many types of Entities that VS Visualizer uses. This section describes some of the most
common Entities.

Animation Manager
The Animation Manger is responsible for managing the simulation time. It may contain other
Entities, including: Runs, Data Sources, Cameramen, and the World Reference Frame.

Simulation Run
A Simulation Run (often referred to as simply a “Run”) encapsulates aspects of a single
simulation Run from a VehicleSim product. A Run contains Reference Frames that define the
locations and movements of objects.

Data Source
A Data Source is a group of related Data Channels. The results from a simulation Run of a VS
Solver (an ERD file and a BIN file) are a Data Source. A Live data connection to a VS Solver is
also a Data Source.




                    Figure 43. VS Visualizer Entities and their relationships




                                            44 / 107
Data Channel
A Data Channel is an Entity that represents a function of time. A Data Channel can be a constant
(e.g., f(time) = 5). A Data Channel can also be the name of a time series loaded from the results
of a simulation Run – each variable in an ERD or VS file (output from a VS Solver) is a Data
Channel when it is loaded into VS Visualizer. For example, the variable Xo, which is often found
in VS Solver output files, is a Data Channel.
Algebraic expressions are also Data Channels. For example the expressions “14.3 * sin(Xo) + 12”
and “180.0 / 3.141593” are Data Channels, and could be used anywhere that a Data Channel can
be specified. See Chapter 19: Algebraic Expression Support (page 74), for more information
about using expressions.

Reference Frame
A Reference Frame defines a coordinate system that may be transformed (translated, rotated, and
scaled) relative to its parent coordinate system. Reference Frames are used to position and orient
objects in 3D space. For example, 3D Shapes and Sounds are placed in Reference Frames to
position them within the 3D scene.
The dynamic properties of Reference Frames are controlled by Data Channels. For example, to
animate a vehicle, a Reference Frame’s translation and rotation properties are assigned to Data
Channels from the ERD file that represent the motions of the vehicle (Xo, Yo, Zo, Pitch, Yaw,
Roll). A 3D Shape representing the vehicle body is placed in the Reference Frame so that when
the animation is played the motion variables from the ERD file control the position and
orientation of the 3D Shape over time.

Shape
A Shape is a 3D model of an object to be rendered.

Sound
A Sound is an Entity that contains audio information that is rendered as part of the 3D scene.
Sounds are “rendered” aurally similar to the way Shapes are rendered visually.
A Sound Entity is more complex than simply an audio file; it has properties that tell VS
Visualizer how to render it within the 3D scene. These properties include settings for looping the
Sound, and bindings to Data Channels that can control starting/stopping the Sound, as well as the
Sound’s volume and playback frequency (pitch).

Cameraman

Entity Parsing
VS Visualizer creates new Entities while reading a Parsfile. New Entities are created when
certain keywords are encountered. Keywords that create new Entities include SET_RUN_SLOT
(creates a new Run), ADD_REFERENCE_FRAME (creates a new Reference Frame), and

actively parsing object. We often refer to these objects as active in the context of parsing.

an Entity is created/activated and when it is deactivated is referred to as the scope of the Entity.
There are generally two ways that an Entity can be deactivated: Explicitly, with a scope-ending
keyword, or implicitly with the creation/activation of another Entity of the same type. For
example, the END_REFERENCE_FRAME keyword will explicitly deactivate the currently active
Reference Frame. The ADD_REFERENCE_FRAME keyword will implicitly deactivate the
previously active Reference Frame (if there was one) because there can only be one active Entity
of a given type.

17. Basic Concepts of 3D Animation
The simulated world is made is made of 3D objects, shown as they would appear if viewed
through a video camera. This chapter describes the basic concepts underlying the representation
of the objects using shapes and motion information.


Shapes
Visible objects are represented by Entities called Shapes. Shapes are typically loaded into VS
Visualizer from 3D model files. Supported 3D file formats include STL, OBJ and OSG. When
Shapes are loaded by VS Visualizer, they are attached to Entities called Reference Frames.




                                             47 / 107
Motion and Reference Frames
The spatial relationships between the various objects (Shapes, Sounds, etc.) in the simulated
world are defined with Reference Frames that can move relative to each other.
A Reference Frame defines a coordinate system which objects in the scene are placed in.
Although a Reference Frame might move and rotate relative to its parent coordinate system, the
spatial relationships between objects (Shapes, Sounds, etc.) in a given Reference Frame do not
change relative to each other.
Figure 44 shows the origins and axes of the Reference Frames for the vehicle’s sprung mass
(body), and its two front wheels (the origin is the point where the axes meet). The sprung mass
Reference Frame contains several 3D Shapes, including the vehicle body and the driver. Each of
the wheel Reference Frames contains three individual 3D Shape objects: the wheel, the tire and
the tire rotation indicator stripe (visible on the front left tire).
In VS Visualizer, all motions are associated with Reference Frames. Each Reference Frame has a
three-dimensional Cartesian coordinate system that is used to describe locations of points of the
Shapes and Sounds in that Reference Frame. The direction of the positive X-Axis is considered
the “forward” direction, the positive Y-Axis is “left”, and the positive Z-Axis is “up”.
In general, it is not possible to tell how many Reference Frames exist by looking at a single
image. However, by observing an animation, it is sometimes possible to see the effects of
individual Reference Frames. For example, a typical animation of a four-wheeled vehicle
includes at least six Reference Frames:
   ·   A fixed global Reference Frame is used to locate the road and other fixed objects such
       as traffic cones and trees.
   ·   A moving Reference Frame contains the vehicle body.
   ·   Four individual Reference Frames each containing one of the vehicle’s wheels.




                                            48 / 107
           Figure 44. Reference Frames: X-Axis (red), Y-Axis (yellow), Z-Axis (blue)
In addition, if moving arrows are used to show tire forces, then each arrow has a separate
Reference Frame. For example, an animation of a four-wheeled vehicle with three force arrows
per tire (Figure 45) would have the six Reference Frames listed above, plus 12 additional frames
for tire force arrows (three per wheel).




  Figure 45. Each tire force arrow requires its own Reference Frame because it is moved and
                             scaled independently of other objects.




                                           49 / 107
Each Reference Frame has a single associated coordinate system. The X-Y-Z axes of the
Reference Frame are used, and there is a single origin used to define local X, Y, and Z
coordinates.
3D Shapes are all defined using local X-Y-Z coordinates of vertices of triangles that make up the
3D surface. VS Visualizer transforms the local X-Y-Z values to global X-Y-Z values in order to
draw the shape. To perform the transformation, VS Visualizer must know the location and
orientation of the Reference Frame relative to the global Reference Frame. This is defined by six
variables: three coordinates and three rotation angles.
The three coordinates for a Reference Frame (X, Y, Z) define the origin of its coordinate system
within its parent coordinate system. The orientation of a Reference Frame is defined by three
consecutive rotations called Euler angles. Starting such that the X, Y, and Z axes of the child
Reference Frame are parallel with those of its parent Reference Frame, the child frame can be
oriented by consecutive rotations about its axes. For example, first rotate the child frame about its
Z axis by a yaw angle. After this is done, the new Z direction is the same as the old, but the X and
Y axes are pointed in new directions, called X' and Y'. Next, rotate about the new Y axis, Y', by a
pitch angle. After the pitch rotation, the Y axis is still in the Y' direction, but the X and Z axes are
pointed in new directions, called X" and Z". Finally, rotate a third time, about the most recent X
axis, X", by the roll angle.
Any conceivable orientation of a Reference Frame can be described with three Euler angles. Note
that the values of the angles depend on the order of the rotations: for a given orientation in space,
the three angles required for sequential rotations about the Z-Y-X axes are different than the three
angles that would be used if the sequence were X-Y-Z.
VS Visualizer supports two Euler angle sequences: Z-Y-X, used for sprung masses, and Z-X-Y,
used for spinning wheels.


Shape and Reference Frame Scaling
VS Visualizer can scale shapes and Reference Frames to allow the same shape information to be
applied to different vehicles with different dimensions. Operations that can transform 3D shapes
include:
    1. Each 3D shape can be scaled and translated independently in each axis. These operations
       have the effect of resizing the object, and shifting its location within the Reference
       Frame.
    Each 3D shape can be rotated about its local X, Y, and Z axes.
    A Reference Frame can be transformed by X, Y, and Z scale factors based on static ratios of
       two parameters: [new length]/[original length]. This has the effect of scaling all of the
       objects in the Reference Frame.
    A Reference Frame can be transformed by X, Y, and Z scale factors based on dynamic gains
       that are obtained from the same source as other dynamic variables.




                                               50 / 107
        Note    VS Visualizer expects all angles to be in degrees, and all coordinates to
                be in the same units of length. All VehicleSim products use meters for
                animation length units.

The first three transformations are applied when the shape information is read from a Parsfile.
Static scaling is usually used to resize shapes to match simulation details. For example, wheels
are resized to convert the original shape files data to match the tire radius used in the simulation
math models.
Dynamic scaling is used, for example, to display force arrows whose lengths are proportional to
forces. The scale factors are read along with other motion variables from the file containing other
motion information.
In addition to scaling, the translucency and visibility of all shapes associated with a Reference
Frame can be changed dynamically based on variables read along with the motion variables. The
dynamic control of translucency can be computationally intensive, so a simple visibility control is
also provided for simpler changes, such as show on/off brake lights.

Lighting Conditions
The lights within the 3D scene affect the appearance of objects in VS Visualizer. Two light
sources affect the appearance of objects:
   1. Global Ambient Light. This is the baseline amount of light present everywhere within
      the 3D scene, applied evenly to all surfaces rendered regardless of their location or
      orientation. The keyword cam_global_ambient is used to modify the global
      ambient light.




                                           59 / 107
    2. Sun Light. The “Sun” in VS Visualizer is a light source that does not move. The diffuse
       and specular components of the light from the sun are both positional and directional.
       The amount of light a surface receives from the sun’s diffuse and specular components is
       based on the positions of both the Sun and the surface, and the angle of the surface
       relative to the sun. The sun’s ambient component is independent of position and
       orientation. The keywords cam_global_diffuse and cam_global_specular
       are used to modify this light.

lighting and fog effects have reasonable values for most normal usage. Table 6 shows keywords

specify only three parameters for any color value, the alpha channel will be set to the default of

documentation.

OpenGL lights can be either directional or positional light sources. For a positional light, light
emanates outward from the specified point in all directions. For a directional light, all light in the
scene travels in the specified direction. Directional lights are less realistic than positional lights,
but may improve graphics performance (particularly on older video hardware).

Position and Orientation of the Reference Frame
A Reference Frame is defined by six variables: three coordinates (X, Y, and Z), and three Euler
angles. VS Visualizer reads the six variables from the output files generated by the solver
programs, if they are specified. If not specified, VS Visualizer uses a value of zero for that
variable.
After loading time histories of the specified variables, each coordinate and Euler angle is
calculated with a relationship of the form:
                               coordinate = Co + C * SFc
                                 angle = Ao + A * SFa
where C and A are the translation and angle variables obtained from the ERD file, Co and Ao are
the constant offsets, and SFc and SFa are scale factors (gains). The offsets and scale factors can
be specified by the keywords shown in Table 8 (set_offset_var_x,
set_offset_var_y, etc.) The scale factors are commonly used in standard VehicleSim
products to convert wheel spin angles from revolutions to degrees.

Transforms

Reference Frames with the additional capability that they can be nested within other Transforms

Usage
The following components can be used to build expressions.

Numeric literals
A numeric literal is used to represent fixed values in the input string.

represents the value 1234.

in either upper or lowercase. For example, the value 0xBA01 is equivalent to the decimal value
47,617.

In addition to rendering a visual representation of the simulation, VS Visualizer can also render
an audio representation. VS Visualizer uses OpenAL, a cross-platform API for rendering multi-
channel three-dimensional positional audio. The OpenAL installer may be found on your product
installation CD. You can learn more about the OpenAL project and download the latest version
from www.openal.org


Overview
The VS Visualizer audio system operates by dynamically modifying sounds that repeat in a
continuous loop. For instance, to represent wind noise of a vehicle, an audio sample of wind is
played continuously in a loop while the playback volume and frequency are varied according to
the air speed relative to the vehicle.
Parsfile keywords are used to specify the audio file to load, which Data Channels are to be used
to dynamically modify the playback parameters, and how the parameters will be modified by the
Data Channels. These keywords create and configure two types of Entities: Sounds and Sound
Modifiers.
Sound Entities are created using the add_3d_sound keyword, and Sound Modifier Entities are
created using the add_sound_modifier keyword. It is also essential to provide an “output”
from the VS Solver (a Data Channel) as an “input” to a Sound Modifier.
Sounds added to your Run are attached to the currently active Reference Frame (specified with
add_reference_frame). If the sound file is monaural (one channel), it will be a positional
sound, and will move with the Reference Frame to which it is attached. If the sound file has two
(stereo) or more channels, the sound will not be positional, but will play normally regardless of
the position or velocity of its Reference Frame. Positional sounds are attenuated with distance
from the viewer, and also have Doppler effect applied to them based on their velocity relative to
the viewer.
For 3D positional sound to work properly, you must ensure that the operating system’s speaker
settings agree with the physical arrangement of your speakers and with any hardware-specific
settings. Consult the documentation for your operating system and your audio hardware to learn
more about multi-channel speaker configuration.
Sound Modifiers use a 4x2 lookup table to determine how their inputs will modify the sound they
are associated with. These tables have four entries, each of which contains an input value and an
output value. The Sound Modifier tables are specified with SOUNDMOD_INPUT_* and
SOUNDMOD_OUTPUT_* keywords.


Example: Wind noise
Listing 9 shows a Parsfile with settings to generate wind noise. When the air speed, specified by
the Data Channel vAir is 0 km/h, the volume modifier will multiply the volume by 0 so that the
wind will not be audible when the car is not moving (relative to the air around it). When the
airspeed is 80 km/h, the sound’s natural volume will be multiplied by 0.03125. This will make the
wind noise audible but not very loud. The input/output parameters of the 4x2 sound modifier

table are linearly interpolated with flat-line extrapolation beyond the boundaries of the input. For
instance, if the vehicle reaches a speed of 300 km/h, the volume will only be multiplied by 0.25.

21. Live Animation
In addition to being able to load pre-computed motion data from simulation output files
(ERD/BIN), VS Visualizer can also connect to a Live Data Server (LDS) to receive “Live”
motion data. When receiving Live data, VS Visualizer can animate vehicle motions as they are


                                           80 / 107
provided in real-time. Typically, a VS Solver acts as the LDS. To act as an LDS and provide Live
animation data, the VS Solver may require a special license, such as Real-Time, Driving
Simulator, or Extra Live Animator.
The difference between off-line animation and Live animation is where a Data Source Entity (and
its Data Channels) get motion data. For off-line animation, the Data Source Entity loads data
from ERD and BIN files (which a VS Solver previously produced), whereas for Live animation,
the Data Source Entity receives data as it is produced by the VS Solver via a TCP/IP network
link.
Note that Live animation is not currently supported on Linux.

22. Heads-Up Display (HUD)
VS Visualizer can enhance your animation by adding Heads-Up Display (HUD) elements as an
overlay on top of the rendered scene to display pertinent information.


Overview
The Heads-Up Display (HUD) is a two-dimensional layer that VS Visualizer draws over the top
of the rendered scene in the animation window. The HUD is unaffected by the motion of the
camera.
A HUD Element is a single object displayed on the HUD. For example, the tachometer in Figure
48 is comprised of two individual HUD Elements: the background image of the gauge dial face,
and the indicator needle.
HUD Elements can be set to align to different sections of the screen. They can scale as the render
window resizes, or remain a fixed pixel size. Their properties (e.g. position, rotation, size, color,
etc.) can be dynamically modified using Data Channels. For example, the rotation of tachometer
needle element seen in Figure 48 is dynamically controlled by the AV_Eng Data Channel.
Press Ctrl+Shift+H while the animation window has focus to display debugging output for the
HUD Elements, such as the bounding boxes seen in Figure 48. The extent of each element is
outlined, and a small crosshair is draw where the element’s centroid is defined. This can help
visualize the element’s alignment, scaling, and rotation.




                                              83 / 107
                  Figure 48. Press Ctrl+Shift+H to identify HUD Elements.

23. Advanced Topics
This section includes less commonly used features of VS Visualizer.


Configuration and Log File Location
VS Visualizer stores configuration and log files in a location called the VS Visualizer Data
Folder. The VS Visualizer Data Folder can be found at the following location:
        "%LOCALAPPDATA%\VS Visualizer"
Where %LOCALAPPDATA% represents the location that the operating system stores the user’s
local application data (e.g. C:\Users\user name\AppData\Local\).
To function properly, VS Visualizer must be able to read from and write to this location.
VS Visualizer stores log file(s) in this folder, while configuration files are stored in the subfolder
named Config. In normal operation, this means that the settings you made the last time you
used VS Visualizer will apply the next time you use it on the same machine.




                                              90 / 107
Manual Monitor Configuration
You can use a monitor setup file if the standard symmetrical setup does not meet your needs. VS
Visualizer will look for a file within the Config directory where the application’s files are stored
for override values to the monitor setup. These files are stored in the user’s data directory,
typically somewhere like this: C:\Users\user                       name\AppData\Local\VS
Visualizer\Config\manual_monitor_grouping.ini.
If the monitor configuration file is found, the values therein will be used regardless of what is
entered in the Tools>Preferences screen setup. This will be noted in the VS Visualizer log file,
which can be accessed via Help>Show Log.

Command Line Control
VS Visualizer can be run from a command line to enable automation and advanced uses under the
control of other software.
Using the normal convention that optional arguments are enclosed in square braces [], required
arguments are shown in angle brackets < >, and alternative options are separated by vertical bars
|, the full command line is:
        VsVisualizer.exe [-h | -help] | [[-c "configuration name"] [-fs <0|1>]
                   [-i name] [-pos x y] [-res width height] [-tb <0|1>]
                   [[-vsrap "output file" [-vsrapoverwrite]] "input
                   parsfile"]]
The named options are:
        -h, –help        Show help string listing these options.
        -c        Launch VS Visualizer using the specified configuration settings. The
                  configuration includes settings from the “Preferences” and “Display Settings”
                  dialogs. If the named configuration does not exist, it will be created. If there are



                                              92 / 107
                  spaces in the configuration name, you must enclose it in double quotes. Do not
                  use punctuation or special characters in the configuration name (the
                  configuration name must be a valid filename).
        -fs       Forces the VS Visualizer full-screen option either on (1) or off (0). If the
                  parameter for this option is 0, VS Visualizer will start in windowed mode; if it is
                  1 it will start in full-screen mode. This temporarily overrides the current
                  configuration setting (which stores the full-screen state of VS Visualizer each
                  time the program exits).
        -i        Specifies the Instance Name for VS Visualizer to use. The instance name is used
                  to set the name of the main VS Visualizer window (the name that appears in the
                  title bar of the main window). If there are any spaces in the specified name, it
                  must be surrounded by double-quotes. The string “VS Visualizer - ” is
                  prepended to the name specified on the command line. For example specifying
                  “-i Test” will cause VS Visualizer’s main window to be titled “VS Visualizer –
                  Test”.
        -pos      Sets the position of the VS Visualizer window on the desktop.
        -res      Set the size of the 3D render window to the specified dimensions: width x
                  height.
        -tb       Control visibility of time control toolbar. Specify “-tb 0” to suppress display of
                  the toolbar, or “-tb 1” to force the toolbar to be visible.

           Appendix A: ERD File Format
The ERD file format was developed by the Engineering Research Division (ERD) of the
University of Michigan Transportation Research Institute (UMTRI) to support automated plotting
of simulation and test data.
An ERD file contains two independent sections; the header and the data. The header contains
only text, and the data section contains only numbers. The numbers can be written in either text
or binary form. The text form is convenient for viewing and editing data with a word processor,
whereas the binary form provides better access for automatic processing. If the data section is in
text format, then both the header and the data are kept in a single file. However, if the data are in
binary format, two files are used. The header is in an ordinary text file with the extension ERD,
and the data are in a file with the name of the header file and the extension BIN. For example, if
the header file is named Out.erd the name Out.bin must be used for the data file. Both files
must be in the same folder.


27. The Header
The ERD file consists of a series of conventional text lines that contain the information used by
post-processing tools to read the numerical data.


Required Lines
As a minimum, the header contains three lines of text. The first line identifies the file as
following the ERD format. The second line describes the way that the numerical data are stored
in the data section of the file. The third required line is an END statement that indicates the end of
the header portion. Any number of optional lines can be included between line #2 and the END
line. Table 28 summarizes the lines in an ERD file, and describes the parameters used in line #2
to describe the numerical data.
The second line of the file shown in Table 28 shows that the file contains data for 2 channels,
with 529 samples/channel, stored as 1 binary record consisting of 4232 bytes, that the data
storage format is type 1 (4-byte binary), that the interval between samples is 1.00, and that the
status of the auxiliary numbers is -1.

Optional Lines with Keywords
Optional lines in the header begin with an eight-character keyword that define a particular type of
data contained in the remainder of the line. Keywords are associated with one of five general data
types: integers, floating point (real) numbers, 8-character names, 32-character names, and 80-
character names. The number of data items is either one per file (e.g., TITLE of data set in the
file), one per channel (e.g., a short name for each channel), an arbitrary number N (e.g., static
axle loads for N axles), or repeatable.
Names associated with a keyword are often shorter than the space allowed. When more than one
name is on the same line, the names are padded with blanks as needed so that following names
begin at the correct column positions. For example, the header shown in Table 28 includes names
of the units for each channel, as identified with the keyword UNITSNAM. The name of units for
the first channel, ft, has only two characters. Thus, it is followed by six spaces so that the name
for the second channel, ft, begins in the correct column position.


28. The Data Section
The data section of the ERD file contains nothing but numbers, organized into columns and rows.
The form in which the numbers are stored depends on the value of the KEYNUM parameter from
line 2 of the header (see Table 28). The total number of values that will appear in the data section
is NCHAN ´ NSAMP. All of the numbers in the data portion are stored in the same format, and
there can be no missing values.

Text Data
The text format can be used for transporting data in ERD files between different computers, and
sometimes even for reading the same file with different programs on the same computer. It is also
convenient when numbers are typed in manually, or when numbers are to be edited using a text
editor. However, there are penalties for using text representations of numbers. (The computer
must translate the text numbers into binary form, so it takes about 10 times longer to read a text
file than a binary equivalent. Also, text files take up more disk storage than binary files.)
When data are stored in text form, the numbers are kept in the same file as the header, with the
numbers beginning immediately after the header. The ERD file in Table 28 shows an example of
numerical data in text form. In cases like this, the file is assumed to contain numbers in free form.
The only restriction on free format numbers is that adjacent numbers must be separated. For
example, the following line is not valid, because the third and fourth numbers touch.
1.2000 3.0000 4.0000-2.01E-01 14.3000
Numbers may be separated by one or more spaces, the tab character, or a comma.


Binary Data
Reading and writing binary data is efficient because the computer does not need to perform any
conversions or transformations as the data values are moved between the file and the computer
memory. When a binary format is used, the data portion of an ERD file is a direct copy of a
portion of the computer memory, corresponding to a two-dimensional array having dimensions



                                             105 / 107
sized to the number of channels and the number of samples. As indicated in Table 28, two forms
of binary data are supported: 2-byte integer and 4-byte floating point. 2-byte integer data are
typically obtained by data-acquisition systems. Each integer value is a sampled reading obtained
from a digitizer during a test. For most engineering applications, data are stored (in the computer
memory) in 4-byte floating point format, also known as single-precision.
The ERD file format has been used on a variety of computer systems and for a variety of mass
storage media. On some systems, binary data are stored in discrete records. A computer program
reading such a file needs to know how many bytes each record contains, and how many records
are in the file. Thus, the header contains these two parameters: NBYTES and NRECS. For most
ERD files, NRECS is the same as NSAMP, and NBYTES is 4•NCHAN.
